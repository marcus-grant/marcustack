# marcustack v0.1 plan

The MVP plan for marcustack.
v0.1 delivers a single-pipeline orchestration spine
and exercises it against the gallery pipeline.

## Scope

v0.1 delivers the orchestration spine for the personal-site stack.
It exercises that spine against exactly one pipeline: the gallery.
Concretely:

- A stage contract any future pipeline can use without modification.
  It covers outcome capture, output atomicity,
  and failure isolation between stages.
- The gallery pipeline composed against that contract.
  Three stages: a NormPic stage, a Galleria stage, and a deploy stage.
  Deploy targets the gallery zone on BunnyCDN.

The spine is the durable artifact.
The gallery pipeline is the first concrete proof it works.

What v0.1 does not orchestrate, left to later versions:

- The personal-site rendering pipeline.
- The retro-theme CSS publish flow.
  The renderer fetches the pinned bundle at build time;
  the composer does not push it.
- The zk-notes wiki.
- Any multi-pipeline or parallel orchestration shape.
- Any configuration assuming more than one source repo or deploy target.

These projects exist and matter to the stack.
The contract earns its keep against one pipeline first.
See **Related projects** for ecosystem context and per-project status.

## Stage contract

The stage contract is the spine's core abstraction.
It defines how a stage runs, declares its outcome, isolates its output,
and how stage failures isolate from one another.

API surface: `run_stage NAME -- CMD ARGS...` for inline stages.
File-based stages live in `stages/<name>.sh` and are invoked by name.

Outcome storage: per-run directory `runs/<timestamp>/<name>.status`,
content is `success` or `failure`.

Output atomicity: the spine creates a per-stage scratch dir at
`$STAGE_OUTPUT`, passes it to the stage,
renames to `_build/<name>/` on success, discards on failure.

Failure isolation: a stage's failure does not abort the spine.
Later stages still run.
A run summary prints at the end.

TDD specs to implement, in order:

1. `run_stage` writes `success` when the command exits 0.
2. `run_stage` writes `failure` when the command exits nonzero.
3. `run_stage` does not abort the spine on stage failure.
4. The spine renames `$STAGE_OUTPUT` to `_build/<name>/` on success.
5. The spine discards `$STAGE_OUTPUT` and leaves `_build/<name>/`
   untouched on failure.
6. Two stages run in sequence; the second runs even if the first fails.

## Gallery pipeline composition

Three stages, executed in order by a pipeline script
(the target of `just deploy`).

- Stage 1: NormPic.
  - Form: file-based stage at `stages/normpic.sh`.
  - Reads: photo source directory (from config).
  - Invokes: NormPic via uv.
    Exact invocation script undecided; almost certainly uv-based.
  - Writes: `$STAGE_OUTPUT`, contains the manifest NormPic produces.
  - Deferred: NormPic CLI shape and exact output layout.

- Stage 2: Galleria.
  - Form: file-based stage at `stages/galleria.sh`.
  - Reads: NormPic's output at `_build/normpic/`,
    plus the photo source if Galleria needs the originals.
  - Invokes: Galleria via uv.
    Exact invocation script undecided; almost certainly uv-based for MVP.
    Expected to change post-MVP as Galleria itself evolves.
  - Writes: `$STAGE_OUTPUT`, gallery HTML and assets.
  - Deferred: Galleria CLI shape, the NormPic-Galleria handoff,
    retro-theme integration shape.

- Stage 3: deploy.
  - Form: inline, via `run_stage deploy -- <upload command>`.
  - Reads: `_build/galleria/`.
  - Writes: BunnyCDN gallery zone.
  - Deferred: BunnyCDN tool, gallery zone name, password-store path,
    subdomain.
    All waiting on NormPic planning to land the choice for the ecosystem.

Looking just past MVP (not in v0.1, but the pipeline grows here next):

- A personal-site stage runs after galleria.
- personal-site is an 11ty SSG.
  Content lives in a separate repo, personal-site-content,
  symlinked into personal-site.
- Before 11ty builds, a before-hook ensures the symlinked content
  repo is up to date.
- Open question to investigate carefully:
  should personal-site handle the content-repo refresh itself
  (via its 11ty before-hook),
  or should marcustack handle it as its own stage or sub-step?

## Configuration

Config lives in `config.toml` at the repo root.
Per-machine; never committed.
A `config.toml.example` is committed as the template.

Schema for v0.1:

- `[source]`: `full_dir` and `web_dir` (local paths NormPic reads),
  `expected_count` (photos expected in each collection).
- `[output]`: `manifest_dir` (where NormPic writes),
  `full_name` and `web_name` (collection names in generated filenames).
- `[normpic]`: `version` (pinned git tag, installed as a CLI).
- `[deploy]`: `zone` and `key_ref` (placeholders; values deferred).

Build output paths are not configurable.
The spine writes each stage's canonical output to `_build/<name>/`,
resolved against the repository root rather than the working
directory.
Keeps the config surface small.

Secrets are referenced, not stored.
`key_ref` points to a password-store path or env var name.
Resolution happens at deploy time, never written in cleartext.

TDD specs for config loading:

1. Loader emits expected env vars for a minimal valid TOML.
2. Loader fails clearly on missing required fields.
3. Loader resolves `key_ref` against a stubbed password-store
   and exposes the secret only via a transient env var.

## Repository layout and justfile recipes

Target directory tree:

```
marcustack/
|-- LICENSE
|-- README.md
|-- .gitignore
|-- justfile
|-- config.toml.example
|-- doc/
|   |-- README.md
|   |-- TODO.md
|   \-- v01.md
|-- scripts/
|   |-- lib/
|   |   |-- stage.sh
|   |   \-- config.sh
|   \-- pipeline.sh
|-- stages/
|   |-- normpic.sh
|   \-- galleria.sh
\-- test/
    \-- stage.bats
```

File notes:

- `config.toml.example` is the template; `config.toml` is per-machine
  and gitignored.
- `scripts/lib/stage.sh` is the spine: `run_stage`, outcome capture,
  output atomicity, run summary.
- `scripts/lib/config.sh` is the config loader.
- `scripts/pipeline.sh` is the gallery pipeline script,
  target of `just deploy`.
- `stages/normpic.sh` and `stages/galleria.sh` are the file-based stages.
  Deploy stage is inline in the pipeline script.
- `test/stage.bats` is where the first failing test lives.

Runtime artifacts (gitignored, never committed):

- `_build/<name>/`: canonical output for each stage,
  written by the spine via scratch-dir-then-rename.
- `runs/<timestamp>/<name>.status`: per-run outcome files.

Justfile recipes:

- `default`: `just --list` to discover what's available.
- `test`: run bats against `test/`.
- `lint`: shellcheck against `scripts/` and `stages/`.
- `deploy`: run `scripts/pipeline.sh` (the gallery pipeline).
- `clean`: wipe `_build/` and `runs/`.

## Testing approach

Tests in v0.1 are bats specs against the spine and config loader.
No real tool invocations; mocks stand in for stages.

Mock conventions:

- Simple success/failure: `true` and `false` as the stage command.
- Side-effect mocks: small inline shell functions or temp scripts.
  They write to `$STAGE_OUTPUT`, set exit codes,
  or simulate misbehavior (e.g., a stage that fails after partial
  output, to verify atomicity).

What does NOT live in the bats suite:

- Actual NormPic, Galleria, or BunnyCDN invocations.
- End-to-end pipeline runs against real photos and zones.
- These are integration concerns,
  gated on those tools and targets being usable.
  Validated manually for MVP.
  A coarser harness may earn its keep later, but is not in v0.1.

Test layout:

- `test/stage.bats`: spine specs
  (the TDD checklist from **Stage contract** lives here).
- `test/config.bats`: config-loader specs.
- Shared setup (temp dirs, env scaffolding) factored into helpers
  if and when it earns repetition.

TDD discipline:

- The first failing test is the first item in the spine TDD checklist:
  `run_stage` writes `success` when the command exits 0.
- Each subsequent green build adds one more checklist item.

## Open items and sequencing

Open items, each with what unblocks it:

- BunnyCDN deploy mechanism (which tool: CLI, curl, rclone).
  Waiting on: settled alongside the deploy-mechanism choice.

- Gallery zone name, password-store path for its key, gallery subdomain.
  Waiting on: infrastructure decisions; ungated on planning,
  but typically settled alongside the deploy-mechanism choice.

- NormPic CLI shape and exact output layout.
  Waiting on: nothing. NormPic `v0.1.1` CLI is frozen and installed.

- Galleria CLI shape.
  Waiting on: Galleria v0.1.0 planning.

- NormPic-Galleria handoff
  (manifest format, whether Galleria reads photos directly
  or only via the manifest).
  Waiting on: Galleria `v0.1.0` planning. The NormPic side is frozen.

- retro-theme integration in Galleria
  (how Galleria fetches the pinned CSS bundle at build time).
  Waiting on: Galleria v0.1.0 planning.

- Personal-site stage design (post-MVP add).
  Waiting on: gallery MVP shipped, personal-site planning,
  and the open question of who owns the personal-site-content refresh
  (personal-site's 11ty before-hook vs marcustack as its own stage).

Work that can proceed in v0.1 without any of the above:

- Spine TDD: full **Stage contract** checklist is achievable against mocks.
- Config loader TDD: TOML schema is locked, so all three specs are
  buildable now.
- Pipeline script structure: `scripts/pipeline.sh` can be written with
  placeholder stage scripts, then those placeholders are replaced as
  upstream planning lands.

## Related projects

Each entry: brief status, relationship to marcustack.

- NormPic.
  Photo manifest generator. Python.
  Status: `v0.1.1` published, contract frozen.
  Relationship: first stage of the gallery pipeline.
  marcustack invokes its CLI, installed from a pinned git tag.

- Galleria.
  Gallery renderer that consumes NormPic manifests.
  Python (transitional; Rust rewrite anticipated).
  Status: exists; refinements planned for v0.1.0 manifest consumption.
  Relationship: second stage of the gallery pipeline.
  marcustack invokes it via `uv run` from a cloned repo path.

- personal-site.
  Static site generator, currently 11ty.
  May change to Astro post-MVP.
  Status: design complete; awaiting bootstrap.
  Relationship: post-MVP addition to the pipeline, runs after galleria.
  Open question on content-repo refresh ownership is in **Open items**.

- personal-site-content.
  Markdown content repo, renderer-neutral.
  Status: design complete; awaiting bootstrap.
  Relationship: input to the personal-site stage (post-MVP).
  Symlinked into personal-site; refresh ownership undecided.

- retro-theme.
  Shared CSS design system on PicoCSS base.
  Versioned immutable bundles via BunnyCDN.
  Status: repo created and pushed, pre-implementation, documentation only.
  Relationship: not orchestrated by marcustack.
  The renderer (Galleria, eventually personal-site) fetches the pinned
  bundle at build time as part of its own build.

- depo.
  URI namespace manager (`depo://` scheme).
  Status: separate active project.
  Relationship: not orchestrated by marcustack.
  Resolution happens at render time inside the personal-site renderer.

- zk-notes.
  Wiki / knowledge base.
  Status: content repo exists; web rendering and search design deferred.
  Relationship: not orchestrated by marcustack in v0.1.
  Integration deferred until the wiki has a rendering layer.

- noncom (non-committal).
  Git daemon for the content layer of the stack.
  Status: separate project; design details TBD.
  Relationship: not orchestrated by marcustack directly.
  It manages the content repos marcustack later reads from.

- cv.
  Status: unconfirmed.
  Surfaced only as a planned retro-theme consumer; no design or repo.
  Relationship: none in v0.1.
  Listed so it is not forgotten.
