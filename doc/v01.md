# marcustack v0.1 plan

The MVP plan for marcustack.
v0.1 delivers a single-pipeline orchestration spine
and exercises it against the gallery pipeline.

## Scope

v0.1 delivers the orchestration spine for the personal-site stack.
It exercises that spine against exactly one pipeline: the gallery.
Concretely:

- A stage contract any future pipeline can use without modification.
  It covers outcome capture, output atomicity,
  and failure isolation between stages.
- The gallery pipeline composed against that contract.
  Three stages: a NormPic stage, a Galleria stage, and a deploy stage.
  Deploy targets the gallery zone on BunnyCDN.

The spine is the durable artifact.
The gallery pipeline is the first concrete proof it works.

What v0.1 does not orchestrate, left to later versions:

- The personal-site rendering pipeline.
- The retro-theme CSS publish flow.
  The renderer fetches the pinned bundle at build time;
  the composer does not push it.
- The zk-notes wiki.
- Any multi-pipeline or parallel orchestration shape.
- Any configuration assuming more than one source repo or deploy target.

These projects exist and matter to the stack.
The contract earns its keep against one pipeline first.
See **Related projects** for ecosystem context and per-project status.

## Stage contract

The stage contract is the spine's core abstraction.

API surface: `run_stage NAME -- CMD ARGS...`.
Every stage is inline; stages call other projects through their
CLI, never their task runner recipes.

Outcome storage: per-run directory
`runs/<timestamp>/<name>.status`, content `success` or `failure`.

Failure isolation: a stage's failure does not abort the spine and
does not stop the stages that follow it.
The pipeline script places explicit `halt_on_failure` gates where
continuing would waste work or mislead: after manifest
verification, after the build, and before upload.
One cause therefore produces one recorded failure, not a cascade.

Output atomicity is not implemented and no longer planned in this
shape: producers write directly into the shared site tree under
`SITE_DIR`, and a scratch-then-rename model does not fit a tree
two producers own jointly.
If partial-output hazards surface, the answer is revisited
against the code.

Implemented specs, covered in `test/stage.bats`:

1. `run_stage` writes `success` when the command exits 0.
2. `run_stage` writes `failure` when the command exits nonzero.
3. `run_stage` returns 0 on failure per failure isolation.

## Gallery pipeline composition

One pipeline script, `scripts/pipeline.sh`, target of
`just pipeline`.
Stages in order, each through `run_stage`:

- `normpic-original`, `normpic-display`: normpic manifests and
  symlinks each source into `SITE_DIR/pics/COLLECTION/original`
  and `display`, manifest colocated in each.
- `verify-original`, `verify-display`, `verify-pairing`: schema,
  symlink integrity, entry count, and cross-variant pairing on
  `relative_path`.
  The pipeline halts here on any failure.
- `galleria`: `uv tool run` pinned to the configured tag,
  `python -m galleria build` with both manifests and
  `--output-dir SITE_DIR`.
  Derive is off by default; `MARCUSTACK_DERIVE=--derive` opts in,
  needed on a clean tree and after source or spec changes.
- `verify-site`: rendition dirs present, per-photo page count,
  collection index a byte copy of page1, no broken symlinks.
  Halts on failure.
- `upload`: armed by `just deploy` (`MARCUSTACK_UPLOAD=1`).
  Bunny HTTP storage API via curl.
  Originals and display copy to the pics zone, skip-existing,
  manifests excluded because they carry local absolute paths.
  Site-owned dirs sync to the site zone with content-hash compare
  and stale-file deletion, scoped to what galleria owns so legacy
  zone content survives.

Looking just past MVP, the pipeline grows a personal-site stage
after galleria: an 11ty build with content symlinked from
personal-site-content.
Open question, recorded in `ecosystem.md`: who owns the
content-repo refresh, personal-site's before-hook or a marcustack
stage.

Known shortfalls are recorded in `TODO.md` under the branch
section.

## Configuration

Config lives at `~/.config/marcustack/config.toml`, outside any
worktree, selected per gallery by `MARCUSTACK_CONFIG`.
`config.example.toml` is committed as the template.

Schema for v0.1:

- `[source]`:
  - `full_dir` & `web_dir`:
    - *(local paths normpic reads)*,
  - `expected_count`:
    - *(photos expected in each collection)*.
- `[output]`:
  - `site_dir`:
    - *(the site root both producers write under)*,
  - `collection_name`:
    - *(one name for both variants, so entries pair on `relative_path`)*.
- `[normpic]`: `version` *(pinned git tag, installed as a CLI)*.
- `[galleria]`: `version` *(pinned git tag)*, run via `uv tool run`.
- `[deploy]`:
  - `storage_host`,
  - `pics_zone`,
  - `site_zone`.
  - *(Bunny storage endpoint and zone names; addresses, never secrets)*.

Credentials are found by convention, never configured:
`~/.config/marcustack/gallery/pics.hdr` and `site.hdr`.
One `AccessKey:` header line each,
shared by every collection because the gallery zones are.
`marcustack` passes those paths to curl and never reads them.

Relative paths resolve against the repository root.
All keys are required;
the loader fails naming any missing key.

## Repository layout and justfile recipes

Target directory tree:

```
marcustack/
|-- LICENSE
|-- README.md
|-- .gitignore
|-- justfile
|-- config.example.toml
|-- doc/
|   |-- README.md
|   |-- TODO.md
|   |-- CONTRIBUTE.md
|   |-- ecosystem.md
|   \-- v01.md
|-- scripts/
|   |-- hook/
|   |   \-- commit-msg
|   |-- lib/
|   |   |-- stage.sh
|   |   |-- config.sh
|   |   |-- verify.sh
|   |   \-- upload.sh
|   \-- pipeline.sh
\-- test/
    |-- fixture.sh
    |-- config.bats
    |-- stage.bats
    |-- verify.bats
    |-- upload.bats
    \-- pipeline.bats
```

File notes:

- `config.example.toml` is the template; the real config lives at
  `~/.config/marcustack/config.toml`, per machine, selected by
  `MARCUSTACK_CONFIG`.
- `scripts/lib/stage.sh` is the spine: `run_stage` and outcome
  capture.
- `scripts/lib/config.sh` loads and validates `CFG_*` values.
- `scripts/lib/verify.sh` checks manifests, pairing, and the site
  tree.
- `scripts/lib/upload.sh` plans and executes zone uploads;
  `upload_plan_dir` is pure and carries the tests.
- `test/fixture.sh` generates the site tree fixtures; no tracked
  binary fixtures.

Runtime artifacts (gitignored, never committed):

- `_build/`: the site root both producers write under.
  Durable; derived renditions live here, so never clean blindly.
- `runs/<timestamp>/<name>.status`: per-run outcome files.

Justfile recipes:

- `default`: `just --list`.
- `test`: full bats suite; `t FILE` runs one file.
- `lint`: shellcheck over scripts and test shell.
- `pipeline`: run `scripts/pipeline.sh`.
- `check`: lint then test, the pre-commit gate.
- `clean`: wipe `_build/` and `runs/`.
  Destroys derived renditions; the next build needs
  `MARCUSTACK_DERIVE=--derive`.
- `install-normpic`: install the pinned normpic tag.
- `deploy`: retired placeholder; upload runs inside `pipeline`
  behind `MARCUSTACK_UPLOAD=1`.

## Testing approach

Tests are bats specs against the spine, config loader, verifiers,
upload planner, and pipeline composition.
No real tool invocations; stubs and generated fixtures stand in.

Stub conventions:

- Simple success/failure: `true` and `false` as the stage command.
- Producer stubs: stub `normpic` and `uv` binaries on `PATH`
  logging their invocations, asserted from the log.
- Site trees: `test/fixture.sh` generates the producer layout;
  `upload_plan_dir` is tested against listing files, no network.

What does NOT live in the bats suite:

- Actual normpic, galleria, or Bunny invocations.
- End-to-end runs against real photos and zones.
  These are the manual acceptance run: real collection, browser
  click-through, zone counts, and edge-rule header checks.

Test layout:

- `test/stage.bats`: spine specs
  (the TDD checklist from **Stage contract** lives here).
- `test/config.bats`: config-loader specs.
- Shared setup (temp dirs, env scaffolding) factored into helpers
  if and when it earns repetition.

TDD discipline:

- The first failing test is the first item in the spine TDD checklist:
  `run_stage` writes `success` when the command exits 0.
- Each subsequent green build adds one more checklist item.

## Related projects

Each entry: brief status, relationship to marcustack.

- NormPic.
  Photo manifest generator. Python.
  Status: `v0.1.1` published, contract frozen.
  Relationship: first stage of the gallery pipeline.
  marcustack invokes its CLI, installed from a pinned git tag.

- Galleria.
  Gallery renderer that consumes NormPic manifests.
  Python (transitional; Rust rewrite anticipated).
  Status: exists; refinements planned for v0.1.0 manifest consumption.
  Relationship: second stage of the gallery pipeline.
  marcustack invokes it via `uv run` from a cloned repo path.

- personal-site.
  Static site generator, currently 11ty.
  May change to Astro post-MVP.
  Status: design complete; awaiting bootstrap.
  Relationship: post-MVP addition to the pipeline, runs after galleria.
  Open question on content-repo refresh ownership is in **Open items**.

- personal-site-content.
  Markdown content repo, renderer-neutral.
  Status: design complete; awaiting bootstrap.
  Relationship: input to the personal-site stage (post-MVP).
  Symlinked into personal-site; refresh ownership undecided.

- retro-theme.
  Shared CSS design system on PicoCSS base.
  Versioned immutable bundles via BunnyCDN.
  Status: repo created and pushed, pre-implementation, documentation only.
  Relationship: not orchestrated by marcustack.
  The renderer (Galleria, eventually personal-site) fetches the pinned
  bundle at build time as part of its own build.

- depo.
  URI namespace manager (`depo://` scheme).
  Status: separate active project.
  Relationship: not orchestrated by marcustack.
  Resolution happens at render time inside the personal-site renderer.

- zk-notes.
  Wiki / knowledge base.
  Status: content repo exists; web rendering and search design deferred.
  Relationship: not orchestrated by marcustack in v0.1.
  Integration deferred until the wiki has a rendering layer.

- noncom (non-committal).
  Git daemon for the content layer of the stack.
  Status: separate project; design details TBD.
  Relationship: not orchestrated by marcustack directly.
  It manages the content repos marcustack later reads from.

- cv.
  Status: unconfirmed.
  Surfaced only as a planned retro-theme consumer; no design or repo.
  Relationship: none in v0.1.
  Listed so it is not forgotten.
