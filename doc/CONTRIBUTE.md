# Contributing to marcustack

How work is done here.
Other documents point here rather than restating.

marcustack orchestrates other projects as pipeline stages.
It does not reimplement them or compensate for their bugs.

## Security

Structural rules, not judgment calls.
Judgment gets reasoned around.

- Credentials live in `~/.config/marcustack/`, outside any worktree.
  Nothing under the repository root ever holds one.
  A gitignore entry can be broken by `git add -f`; a path outside the
  repository cannot.
- Never read a credential file.
  Test that it exists and is readable, pass the path along, never the
  value.
- `config.toml` holds machine-local paths and counts, nothing else,
  and is therefore safe to read, grep, and paste.
  If a secret seems needed there, add a second file outside the
  repository.
- Never run `env`, `printenv`, `set`, or bare `export`.
  Read only environment variables the maintainer names.
- Every proposed command runs on the maintainer's machine and its
  output is pasted back, so the relay is an exfiltration path.
  The burden is on whoever writes the command.
- No `set -x` in committed code; it prints every value.
- A failing stage names the missing key or path, never dumps the
  config.

## Paths

- `~/.config/marcustack/`: credentials.
- `~/.cache/marcustack/`: reserved, nothing writes here yet.
  Caches go here, not `_build/` which `just clean` wipes, and not an
  output tree a consumer reads.
- `_build/`, `runs/`: repository-local, gitignored, wiped by
  `just clean`.

## Dependencies

`bats`, `shellcheck`, ImageMagick, and `python3`.

`python3` is needed by `scripts/hook/commit-msg` on the machine you
commit from, and may be ported to a static binary later.
The hook is tracked and `core.hooksPath` points at it, so there is no
install step to drift.
On a fresh clone: `git config core.hooksPath scripts/hook`.

## Upstream projects

Upstream projects are consumed as released artifacts, through their
command line interfaces and documented contracts.
Never their internals, never their task runner recipes.

An upstream contract is whatever that project documents as its
consumer surface, and nothing else.
For normpic v0.1.0: `doc/architecture/manifest-contract.md`,
`schema/v0.1.0.json`, `doc/guides/manifest-integration.md`.
Read them from the upstream repository.
Never copy one here; a copy is a second definition and will drift.

When a failure traces upstream, file it upstream.
Do not add compensating logic here.

## Ways of working

Plan, review, implement, verify, submit.

- Author: plans, implements, summarizes each commit.
- Reviewer: signs off the plan before any code, runs QA before submit.
- Maintainer: approves and merges.

No implementation before the plan is signed off.
The plan is the baseline review grades against.

## Planning

A plan is an ordered task list precise enough to execute top to bottom.

- First task is branching: `git checkout -b <prefix>/<slug>`.
- Body is spec-then-test-then-implement cycles grouped by behavior.
  Each names its spec, its test, and its implementation.
  Related cases for one rule stay in one cycle.
- Where a behavior has a boundary or trap (missing file, path with a
  space, empty collection), the plan names the test closing it.
  A named boundary test is what review verifies directly.
- Each cycle cites its spec source: the stage contract and
  `doc/v01.md` locally, or an upstream document by path.
- Scope stated concretely: which files, roughly how much.
  A disproportionate diff later signals drift.
- Closes with a `Doc:` commit, then a `Pln:` commit updating
  `doc/TODO.md`.
  Skipping either is deliberate, not default.

A plan recorded in `doc/TODO.md` takes the same shape under a
branch-named section, executable without reconstruction.

## Test-driven development

Default for any change that alters behavior.

Red, green, refactor is a working rhythm, not a commit boundary.
One behavior at a time; run the relevant tests after each testable
addition.
Every commit leaves the suite green.

`bats` is the test runner; `just` invokes it.

Everything here is observable from outside a command, so tests assert
on exit status and output.
Assert on what marcustack observes, never on how an upstream producer
arrives at it.

Fixtures are generated by a committed script into `_build/`.
The script is the single source; a tracked binary fixture is a second
definition that drifts silently.

The fast suite runs against small generated fixtures.
A real photo collection is large, lives outside the repository, and is
reserved for the manual acceptance run.
Tests invoking an upstream tool are slow and need it installed.

## Commits and branches

### Pre-commit gate

1. `just lint`, `shellcheck` over this repository's shell.
2. `just test`, the full `bats` suite.

`just check` runs both in order.
This list is the definition; the recipe follows it.

The gate is repository-local and never recurses into an upstream
project, which is proven by its own gate in its own repository.
Integration is proven by the manual acceptance run instead, which is
too slow for a gate and needs a collection not in the repository.

### Sizing

Group by logical coherence; a commit is self-contained and leaves the
tree green.

Guidelines, not gates: 300 lines is a soft ceiling, two to eight
commits per change.
A slightly larger coherent unit beats fragmenting one behavior.

### Message format

Enforced by `scripts/hook/commit-msg`.

- Title at most 50 characters including prefix, capital or digit after
  the colon.
- Body lines at most 72 characters, `-` bullets, even leading spaces.
- No emoji, links, or co-authored-by lines.

Prefixes: `Pln:` `Ft:` `Fix:` `Ref:` `Doc:` `Chr:` `Tst:`.

### Branch names

Lowercase prefix, slash, kebab-case slug: `ft/normpic-stage`,
`tst/config-loading`.
Refer to work by branch name, never by ordinal.

## Quality assurance

A gated, progressive hunt before submit.
The green suite already proves mechanical correctness, so review only
chases what tests cannot catch: a misread spec, a missing required
thing, a false claim, a latent trap.
Grade against the approved plan, starting from the summary before
reading the repository.

### Author's summary

Subject, one sentence of what changed, pass or fail, and
`git diff --stat`.
The stat is required; scope drift is invisible in prose.

### The ladder

Cheapest first.
Each rung runs only when its failure is possible for this change.

- Summary against plan: watch overclaims and scope beyond the plan.
- Scope from the stat: expected files, proportionate size.
  Stop and flag a disproportionate diff before reading content.
- Signatures by targeted grep: is the substantive change the specified
  one?
- Claims against ground truth, only when the summary makes a
  falsifiable claim.
- Completeness, only when tests discover set members dynamically and a
  missing member would raise no failure.
- Trap reasoning, only when correctness-bearing logic changed:
  vacuous conditions, boundary inputs, one defect producing many
  errors, misattributed errors.

Shell adds its own trap class: a path with a space or glob character,
an unquoted expansion, an exit code swallowed by a pipe, a variable
empty rather than unset.
Fixtures have tidy paths and will not surface these.
`shellcheck` catches most, which is why it runs first.

### Probe kit

Around fifteen lines total, targets derived from the plan.

- Grep assertions in changed test files, not just test names.
- Grep source for the removed token; empty output is the proof.
- Grep tests for the new symbol, confirming it is exercised.

Use `grep -I --include='*.sh' --include='*.bats'`.

These confirm the tests assert the right thing for the cases they
name.
Going past the author's chosen cases needs independent ground truth.

### Deleting a rung

When a failure mode recurs, push it into a suite assertion so it goes
red on its own instead of costing a review pass.

### The reviewer is not exempt

An inferred hazard is a claim, not a finding, until checked against
the code or the contract.
Do not escalate one to the maintainer before reading the source that
would confirm or dismiss it.
If the spec or code answers a question, read it rather than asking.

State a correction once and move on.
Do not restate a corrected position as the original, or re-explain one
fact in varying forms.

### Sign-off

Commits match the plan, scope is contained, claims check out, and the
applicable rungs found nothing.
Open items go back as surgical requests, not a direction to start
over.

## Coordinating across roles

The reviewer is often a coordinator between an author and this
standard.

- Review against the repository, never the prose alone.
- Shell output moves by clipboard relay, so requests are targeted
  greps and line ranges, never "send me the whole file".
- One command per exchange, multiple commands brace-grouped before the
  pipe.
- Never issue `cd`; shell directory state cannot be tracked across the
  relay.
- No inline comments in shell commands.
- Commands and commit messages go in separate blocks, so the message
  pastes cleanly.
- The coordinator writes commit messages; the author does not.
- Every proposed change is fenced with its destination adjacent: the
  file path in backticks and enough context to place it.
  A fence with no destination is incomplete.
- A fence containing an inner fence uses five backticks outside.

A dependency-ordered change is signed off per commit rather than as a
unit: plan, sign off, implement, summarize, sign off, commit, next.
Encode that ordering in its `doc/TODO.md` section with the reason each
step precedes the next.

### Manual acceptance run

The suite proves correctness on generated fixtures, not behavior on
real data.
For changes touching the end-to-end path, run the pipeline on a real
collection before final sign-off.
Check what fixtures cannot: no dangling symlinks, output validates
against the upstream schema, files open through the links, counts
match config.
This has caught producer drift that every fixture test passed.

### Communication

Terse and direct, one topic at a time.
One concrete recommendation, not a menu.
State a correction once; do not relitigate a settled call.
Recalibrate immediately when the maintainer flags drift.
Escalate a scope change rather than folding it in.

## Style

Applies to code, comments, commit messages, and pull request bodies.

- ASCII only.
  No em dashes, no emoji, no decorative Unicode.
- Line length: 72 for commit bodies, 80 for prose and shell.
- In prose, sentence-ending punctuation is followed by a newline.
  A long sentence breaks at a natural point before the limit.
- Singular directory and field names: `doc/`, `test/`, `asset/`.

Shell:

- `#!/usr/bin/env bash` and `set -euo pipefail` at the top.
- Quote every expansion.
- Prefer `[[ ]]`.
- Functions lowercase with underscores, one-line comment stating what
  they do and what they exit with.
- Verify a tool exists before use; fail naming the missing tool.
- Passes `shellcheck` with no suppressions.
  A suppression carries a comment giving the reason.

## Documentation

A fact lives in exactly one place.
The stage contract lives in `doc/v01.md`.
An upstream contract lives upstream and is pointed to, never restated.

Every document is reachable from the root `README.md` through a chain
of links.
Each directory README is its index.
A document links to peers or one level down, never deeper.
No orphans.

Documentation never references the process that produced it: no
conversations, sessions, or assistants.
Every document reads cold to a developer who knows nothing about how
it was written.

`doc/TODO.md` is append-and-prune.
Find a section with `grep -n`, view a few lines, edit surgically.
A completed task is deleted, not marked done.
